01

What Phase 3 delivers

After Phase 2 the profile is static — it's seeded once from your declared interests and never changes. Phase 3 introduces behavioral signals: the system observes how you actually interact with articles and gradually moves your profile toward what you demonstrably read, save, and avoid. This is the difference between a feed that reflects who you said you are and one that reflects what you actually care about.

Three signals are captured: dwell time (how long you spend reading), saves (explicit positive signal), and dismissals (explicit negative signal). Each is weighted differently, combined into a weighted average of article embeddings, and used to nudge the long-term profile vector. A momentum factor (0.85 / 0.15 blend) ensures a single session can't hijack the profile — changes accumulate gradually.

Interaction recording
Frontend sends dwell time, saves, and dismissals to POST /api/v1/news/interactions. Each event is stored in NewsInteraction.
Behavioral profile update
A backend command reads recent interactions, computes a weighted average of article embeddings, and blends the result into NewsUserProfile.LongTermEmbedding.
Dwell normalization
Dwell time is compared against your personal reading baseline — average dwell across all your reads — so absolute seconds don't distort signals.
Scheduled updates
A dedicated ProfileUpdateWorkflow runs at the end of every ingestion run and can be triggered independently for on-demand profile refresh.
02

How the feedback loop works

The update runs once per ingestion cycle (attached to the tail of NewsIntelligenceWorkflow) and operates over a 7-day sliding window of interactions. It does not run per-request — the feed ranking always uses the stored profile vector, not a live computation.

frontend — new
User interacts with an article
Opening the detail view starts a dwell timer. Closing sends a read event with dwell seconds. A save button sends a save event. A "Not interested" button sends a dismiss event without deleting the article.
backend — new
Interaction recorded
POST /api/v1/news/interactions calls RecordNewsInteractionCommandHandler. The interaction is stored in NewsInteraction with type, dwell seconds, and timestamp. User identity comes from the authenticated session.
worker — new (end of ingestion run)
Profile update triggered
update_user_news_profile activity calls POST /api/internal/v1/news/profile/update-from-interactions. The backend command reads the last 7 days of interactions and returns "updated", "no-data", or "no-profile".
backend — new (inside the command handler)
Weighted embedding computed
For each interaction that has a stored embedding, a weight is computed based on type and normalized dwell. A weighted sum of article embeddings is calculated, normalized to a unit vector, and blended with the existing long-term profile at 85% / 15%.
backend — updated
Profile stored, feed re-ranks automatically
NewsUserProfile.LongTermEmbedding and UpdatedAt are written. The next call to GET /api/v1/news/feed uses the new vector automatically — NewsVectorSearch reads it on every request.
↻ All computation stays in the backend. The worker activity is a thin trigger — it sends a single POST and logs the result. The backend fetches interactions, loads embeddings from the DB, computes the weighted average, and writes the updated vector. This is the same pattern as Phase 2: the worker never handles float arrays.
03

Interaction weighting model

Three interaction types carry different semantic weight. Saves are the strongest positive signal — they're deliberate. Dwell time is a weaker but continuous signal that scales with how long you stayed on an article relative to your own average. Dismissals are a negative signal: they push the profile slightly away from that article's topic cluster.

Signal weights — applied to article embeddings
Type Weight Notes
save 1.0 Strongest positive signal. Full weight applied to the article's embedding.
read (long) 0.2 – 0.8 Scales with normalized dwell. At 2× your average read time, weight reaches 0.8.
read (short) 0.2 Minimum weight for any read. Glancing counts, but barely.
dismiss −0.3 Negative weight. Subtracts a scaled version of the article's embedding from the sum.

Dwell normalization formula

To make dwell time comparable across different reading sessions and article lengths, it is normalized against the user's own baseline before weighting. The baseline is the average dwell time across all past read interactions for this user.

# dwell_factor ∈ [0.0, 1.0]
avg_dwell  = mean(dwell_seconds for all user read interactions)
dwell_factor = clamp(dwell_seconds / avg_dwell, 0.0, 2.0) / 2.0

# read_weight ∈ [0.2, 0.8]
read_weight = 0.2 + 0.6 * dwell_factor

# If no prior reads exist, default avg_dwell = 60 seconds

Profile blend formula

A momentum factor ensures the long-term profile doesn't shift abruptly on a single day's behavior. The new profile is a weighted combination of the existing embedding and the behavioral signal from the current window.

# weighted_sum = sum(weight_i * article_embedding_i) for all interactions in window
# (negative weights for dismiss type)

behavioral_signal = normalize(weighted_sum)   # unit vector
new_profile       = normalize(
    0.85 * current_long_term + 0.15 * behavioral_signal
)

# Skip update if weighted_sum is the zero vector (all weights cancel out)
# Skip update if no interactions have stored embeddings
ℹ Why 0.85 / 0.15? At 0.15 per run the profile takes roughly 13 runs to shift meaningfully (half-life of ~6 runs). This lets behavior accumulate over several days before changing what you see, rather than reacting to a single afternoon of reading one topic. The ratio can be made configurable in a later phase.
! Articles without stored embeddings are skipped. If an interaction refers to an article that was ingested before Phase 2 (and therefore has no embedding), it is simply omitted from the weighted sum. The update still runs with whatever interactions do have embeddings. This gracefully handles the backfill gap without crashing.

New data model — NewsInteraction

One new entity. It stores each discrete interaction event — a row per event, not one aggregated row per article. This means you can always recompute the profile from raw events, adjust the weighting formula retroactively, and query patterns like "articles I always dismiss in the first 5 seconds".

// Platform.Domain/Features/News/NewsInteraction.cs
public enum NewsInteractionType { Read, Save, Dismiss }

public sealed class NewsInteraction
{
    public long   Id              { get; set; }
    public int    UserId          { get; set; }
    public string NewsItemId      { get; set; } = "";  // FK → NewsItems.Id, no cascade (keep events even if article deleted)
    public NewsInteractionType Type { get; set; }
    public int?   DwellSeconds    { get; set; }         // null for Save and Dismiss
    public DateTimeOffset RecordedAt { get; set; }
}

EF Core configuration decisions

Table name: news_interactions. The NewsItemId FK is set to NoAction on delete — interaction events are preserved even if the article is later hard-deleted. This is intentional: the profile update command skips interactions without embeddings anyway, so orphaned rows are harmless and historically valuable.

ℹ No unique constraint on (UserId, NewsItemId, Type). Multiple reads of the same article are valid — you might return to an article three times. The weighted average naturally handles repetition: a save followed by three reads applies more total weight to that article's embedding than a single save alone.

Key indexes

IndexColumnsPurpose
Primary key Id (bigserial) Row identity
Profile update query (UserId, RecordedAt) Fetch recent interactions for a user in the sliding window — the hot path for profile updates
FK index NewsItemId Join with NewsItemEmbeddings during profile update computation

Backend — two new commands

Phase 3 introduces two command handlers following the same CQRS pattern used throughout the news feature. Both have validators and both are injected via the existing DI registration approach.

Command 1 — RecordNewsInteractionCommand

Validates the request and writes a single NewsInteraction row. This is called from the user-facing API route, so the UserId comes from the authenticated session (via IMemoryUserContextResolver or equivalent), not from the request body.

// Platform.Application/Features/News/RecordInteraction/RecordNewsInteractionCommand.cs
public sealed record RecordNewsInteractionCommand(
    int    UserId,
    string NewsItemId,
    string Type,          // "read" | "save" | "dismiss" — validated and parsed to enum
    int?   DwellSeconds);  // required when Type = "read", null otherwise

Validator rules: UserId must be positive; NewsItemId must be non-empty; Type must be one of the three known strings; DwellSeconds must be present and ≥ 1 when type is "read"; DwellSeconds must be null when type is "save" or "dismiss".

// Platform.Application/Features/News/RecordInteraction/RecordNewsInteractionCommandHandler.cs
public sealed class RecordNewsInteractionCommandHandler(
    IValidator<RecordNewsInteractionCommand> validator,
    INewsInteractionRepository interactions)
{
    public async Task HandleAsync(RecordNewsInteractionCommand cmd, CancellationToken ct)
    {
        await validator.ValidateAndThrowAsync(cmd, ct);
        var interaction = new NewsInteraction
        {
            UserId       = cmd.UserId,
            NewsItemId   = cmd.NewsItemId,
            Type         = Enum.Parse<NewsInteractionType>(cmd.Type, ignoreCase: true),
            DwellSeconds = cmd.DwellSeconds,
            RecordedAt   = DateTimeOffset.UtcNow,
        };
        await interactions.InsertAsync(interaction, ct);
    }
}

Command 2 — UpdateNewsProfileFromInteractionsCommand

The more complex handler. It fetches recent interactions, loads the corresponding article embeddings from NewsItemEmbeddings, computes the weighted average, and updates NewsUserProfile.LongTermEmbedding. This handler directly queries the DB (via repositories) rather than going through any service boundary.

// Platform.Application/Features/News/Profile/UpdateNewsProfileCommand.cs
public sealed record UpdateNewsProfileCommand(
    int UserId,
    int WindowDays = 7);   // how far back to look for interactions

public enum UpdateNewsProfileResult { Updated, NoData, NoProfile }

The handler uses three repository calls: INewsInteractionRepository.GetRecentAsync(userId, since), INewsEmbeddingRepository.GetByNewsItemIdsAsync(ids, modelKey), and INewsProfileRepository.UpsertAsync(profile). All heavy computation (the weighted sum, normalization, blend) happens in C# using the loaded vectors. No EF queries inside the math — load the data, compute in memory, write one row.

★ Add GetByNewsItemIdsAsync to INewsEmbeddingRepository. The current interface only has ExistsAsync and UpsertAsync. The profile update command needs to load embeddings for a batch of article IDs in one query. Add this method — it's a simple WHERE NewsItemId IN (...) AND EmbeddingModelKey = modelKey query via EF Core.

Worker — new activity and workflow

A single new Temporal activity triggers the backend profile update. It lives in activities.py alongside the existing embedding and seed activities, following the exact same pattern. A thin wrapper workflow wraps it so the update can be triggered standalone (manually or on a schedule) as well as from the tail of NewsIntelligenceWorkflow.

act 1 Python update_user_news_profile timeout 30s

Calls the internal profile update endpoint. All computation happens on the backend. The activity handles the three result states cleanly without raising on "no-data" — if there have been no interactions in the last 7 days, the profile simply isn't updated that run.

  • Accepts user_id: int and optional window_days: int = 7
  • POSTs to /api/internal/v1/news/profile/update-from-interactions
  • Logs outcome: "updated", "no-data" (no interactions), or "no-profile" (Phase 2 seeding hasn't run yet)
  • Never raises on "no-data" or "no-profile" — these are expected states, not errors
# workers-platform/app/workflows/news_intelligence/activities.py — addition
@activity.defn
async def update_user_news_profile(user_id: int, window_days: int = 7) -> dict:
    settings = get_settings()
    base    = settings.platform_api_base_url.rstrip("/")
    headers = {"Authorization": f"Bearer {settings.platform_internal_service_token}"}
    try:
        async with httpx.AsyncClient(timeout=25.0) as client:
            r = await client.post(
                f"{base}/api/internal/v1/news/profile/update-from-interactions",
                json={"userId": user_id, "windowDays": window_days},
                headers=headers,
            )
            r.raise_for_status()
            status = r.json().get("status", "error")
    except Exception:
        logger.exception("update_user_news_profile failed user_id=%s", user_id)
        status = "error"
    logger.info("update_user_news_profile user_id=%s status=%s", user_id, status)
    return {"status": status}

ProfileUpdateWorkflow

A thin standalone workflow that wraps update_user_news_profile. It exists so the update can be triggered via Temporal's UI or API without running a full ingestion cycle. In normal operation it's also called at the tail of NewsIntelligenceWorkflow — one activity call added after ensure_user_news_profile.

# workers-platform/app/workflows/news_intelligence/profile_update_workflow.py
from temporalio import workflow
from app.schemas.workflow_contracts import WorkflowRunRequest, WorkflowRunResult

@workflow.defn
class NewsProfileUpdateWorkflow:
    """Standalone wrapper — triggers profile update from interactions.
    Also called at the tail of NewsIntelligenceWorkflow after each ingest run."""

    @workflow.run
    async def run(self, payload: str) -> WorkflowRunResult:
        request = WorkflowRunRequest.model_validate_json(payload)

        result = await workflow.execute_activity(
            "update_user_news_profile",
            args=[1, 7],   # primary user, 7-day window
            start_to_close_timeout=timedelta(seconds=30),
        )

        return WorkflowRunResult(
            workflow_type=request.workflow_type,
            workflow_run_id=request.workflow_run_id,
            status="completed",
            artifact_refs=[str(result)],
        )

Frontend — dwell tracking, save, dismiss

Three pieces of UI are added to NewsView.tsx. The existing article list and detail view are extended in-place — no new component files are needed for Phase 3. A new API adapter file handles the interaction POST.

1. Dwell time tracking

When the user opens an article (transitions to the detail view), record the timestamp. When they close it (tap "Back to feed" or select a different article), compute the elapsed time in seconds and send a read interaction. Use a useRef for the start timestamp so the value is captured at mount without causing re-renders.

// Inside NewsView.tsx — detail view branch
const dwellStartRef = useRef<number | null>(null);

useEffect(() => {
  if (!selected) return;
  dwellStartRef.current = Date.now();
  return () => {
    const start = dwellStartRef.current;
    if (start === null || !selected) return;
    const dwellSeconds = Math.round((Date.now() - start) / 1000);
    if (dwellSeconds >= 2)  // ignore accidental taps (under 2 seconds)
      void postNewsInteraction(selected.id, "read", dwellSeconds);
  };
}, [selected?.id]);  // re-runs when the selected article changes
! Dwell under 2 seconds is ignored. If the user opens an article and immediately closes it, that's probably a mis-tap, not a read. The 2-second threshold prevents noisy low-weight reads from accumulating. This threshold can be raised later if the signal proves too noisy.

2. Save button

Added to the detail view card, alongside the back button. Sends a save interaction and shows a brief "Saved" confirmation state. This is not a full bookmarking system — Phase 3 only records the signal. Saved items as a browsable feature is a separate concern for a later phase.

// Inside NewsView.tsx — detail view
const [saved, setSaved] = useState(false);

const handleSave = () => {
  if (saved || !selected) return;
  setSaved(true);
  void postNewsInteraction(selected.id, "save");
};

3. Dismiss — "Not interested"

Distinct from the existing "Delete selected" functionality. Delete is a hard permanent removal of the article from the database. Dismiss is a soft interest signal that hides the article from the current view client-side and records a negative-weight event — the article stays in the database for other purposes.

Add a small "Not interested" button on each article card in the list view (visible on hover or as a secondary action). When clicked: record a dismiss interaction, and add the article ID to a local dismissedIds set in component state so it disappears from the list without a full page reload.

// Inside NewsView.tsx — list view
const [dismissedIds, setDismissedIds] = useState<Set<string>>(() => new Set());

const handleDismiss = (id: string) => {
  setDismissedIds(prev => new Set([...prev, id]));
  void postNewsInteraction(id, "dismiss");
};

// Filter dismissed articles out of the rendered list
const visible = filtered.filter(a => !dismissedIds.has(a.id));

API adapter

// frontend-platform/src/modules/news/api/post-news-interaction.ts
import { apiRequest } from "@/lib/api/client";

export async function postNewsInteraction(
  newsItemId: string,
  type: "read" | "save" | "dismiss",
  dwellSeconds?: number,
): Promise<void> {
  await apiRequest("/api/v1/news/interactions", {
    method: "POST",
    body: { newsItemId, type, dwellSeconds: dwellSeconds ?? null },
    cache: "no-store",
  });
}
ℹ Interaction POSTs are fire-and-forget on the frontend. The void prefix on each call is intentional — interaction tracking should never block the UI or show an error to the user if it fails. If the API is unreachable, the user's session still works. Signal loss on network hiccups is acceptable.

Decisions to make before starting

Most of Phase 3 is straightforward given the Phase 2 foundation. Two decisions are worth confirming before implementation starts.

! Decision 1 — interaction endpoint auth. The current feed route uses PlatformWorkerOptions.PrimaryUserId to identify the user (single-user system). The interaction endpoint follows the same pattern. If you later add multi-user support, the interaction handler needs to read from the JWT instead. For now, hardcoding PrimaryUserId is fine and consistent with the rest of the news feature.
! Decision 2 — blend factor configurability. The 0.85 / 0.15 split is hardcoded in the command handler. If you want to tune it without redeploying (e.g., make the profile respond faster to new behavior during testing), make the alpha a backend config value. For Phase 3, hardcoding is fine — add configurability in Phase 4 if needed.
→ Build order within Phase 3. Start with the domain entity and migration so the DB is ready. Then the command handlers (they can be unit-tested immediately). Then the API routes. Then the worker activity. The frontend changes are independent and can be done in parallel with the backend once the API contract is settled.

Start here

Create NewsInteraction.cs, add INewsInteractionRepository, run the migration. Then implement both command handlers and their validators. That's the core — everything else wires on top of it.

What Phase 4 builds on

Phase 4 introduces a dual interest model — a separate short-term embedding (14-day window, no momentum) blended with the long-term at read time. The NewsInteraction table built here feeds both. Phase 4 only adds a new field to NewsUserProfile and updates NewsVectorSearch to blend the two.

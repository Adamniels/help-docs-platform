The 5-phase build is complete. Everything below is additive — none of it requires touching the Phase 1–5 infrastructure, and none of it blocks anything else in the system.

✓ Phases 1–5 complete
Ingestion (Phase 1), semantic embeddings (Phase 2), behavioral feedback loop (Phase 3), dual interest model and active contexts (Phase 4), and LLM re-ranking with per-article explanations (Phase 5) are all shipped and working. What follows are ideas for making the feed smarter, the data cleaner, and the experience better — in no particular priority order.

Ranking intelligence

Ideas that make the ranking itself smarter — going beyond cosine similarity and LLM scoring toward a feed that is aware of what you already know, what you have already seen, and which sources deserve more trust.

intelligence Novelty scoring — penalise articles about things you already know well medium effort

Right now the feed surfaces articles that are close to your interests. That means if you are a software engineer, software engineering articles always score high — even if you know the topic cold. A novelty signal would deprioritise articles on topics already covered heavily in your semantic memory and boost articles that introduce something genuinely new to you.

The implementation approach: before the LLM re-ranking step, compare each candidate article's embedding against the user's existing semantic memory embeddings. Articles with high similarity to stored memories get a novelty penalty applied to their score. Articles on topics not well represented in memory get a boost. This gives Claude better-quality candidates to re-rank.

intelligence Multi-armed bandit for source exploration high effort

The current feed always exploits known good sources — if Hacker News articles consistently score well, they will dominate. A multi-armed bandit approach introduces deliberate exploration: occasionally surfacing articles from sources or topics that have not performed well recently, to give them a chance to prove their value.

The classic formulation is epsilon-greedy or Thompson sampling applied per source. Track a running engagement rate (saves and long reads divided by impressions) per source. Periodically allocate a small fraction of feed slots to sources below their expected performance, and adjust their allocation upward if engagement improves. This prevents the feed from converging to a narrow set of sources.

intelligence Knowledge graph for entity-level understanding (Neo4j + GraphRAG) high effort

Vector similarity captures topical closeness but misses structure. A knowledge graph would represent the entities in your reading history — people, projects, technologies, companies — and the relationships between them. GraphRAG (retrieval augmented generation over a graph) can then answer questions like "surface articles that are adjacent to what I already know but one hop away" or "find articles that connect two of my active interests in a non-obvious way."

This is the highest-effort idea on this list. The right approach is additive: Neo4j alongside the existing Postgres stack, populated incrementally as articles are ingested and as you interact with them. The vector search path remains unchanged; the graph adds a second retrieval path that can be blended in.

Data quality

Ideas that make the underlying article data cleaner before it reaches ranking.

quality Semantic deduplication — one story, not ten versions of it low effort

Currently deduplication is by URL hash. When the same news story is covered by Hacker News, GNews, and an RSS feed, all three versions are ingested and all three appear in the candidate pool. The LLM re-ranking ends up choosing between near-identical articles, wasting candidate slots.

The fix: after embedding but before the candidate fetch, cluster articles by embedding similarity within a sliding time window (say, articles published within 24 hours of each other with cosine similarity above 0.92 are considered the same story). Keep the highest-quality version (longest body, most reputable source, or highest interaction rate) and drop the rest. This is a pure backend change in the ingest pipeline and does not touch any Phase 1–5 code.

quality Source quality scoring low effort

Not all sources produce articles of equal depth. A 200-word news brief from a wire service ranks the same as a 3000-word technical deep dive from a domain expert. A source quality score — based on average article length, average dwell time across all users, and save rate — could be applied as a lightweight pre-filter or as an additional signal in the LLM re-ranking prompt.

This is straightforward to compute from existing interaction data once enough interactions have accumulated. Store a rolling quality score per source domain in a small config table and pass it alongside the article metadata in the candidate fetch response.

quality Per-project topic lists for active context low effort

Right now active projects are stored as plain name strings (e.g. "Platform", "news feature"). The active context embedding is built from those names, which is coarse. A richer model: each project has an associated list of topics it covers. For example, "news feature" maps to ["recommendation systems", "embeddings", "Temporal workflows", "vector search"].

This was mentioned in the Phase 4 plan as a natural extension. The ActiveProjectsJson column in ExplicitUserProfile already stores projects as JSON — extending the schema to include a topics array is a small frontend and backend change. The active context embedding immediately becomes more specific without any changes to the Phase 4 embedding logic.

UX and product

Improvements to how the feed feels and how you interact with it.

ux Saved items as a browsable feed low effort

The save interaction is recorded and influences the profile but the saved articles are not browsable. A simple saved items view — already stubbed in the frontend navigation — would let you return to articles you marked. The interaction data and the article data are already in the DB; this is purely a read query and a frontend page.

ux Digest email low effort

The PlatformUserSettings entity already has a DigestEmail boolean field — it was included when the settings model was built. The infrastructure to send a weekly digest of the top-ranked articles (with their LLM explanations) is not yet wired up. A scheduled Temporal workflow that reads the current news_ranked_feeds row and formats it into an email is a natural next step.

ux Configurable blend weights low effort

The 70/20/10 long-term/short-term/active-context blend and the 0.85 momentum factor are hardcoded constants. Making them configurable in PlatformUserSettings or a dedicated news settings section would let you tune how quickly the feed responds to new behaviour (raise short-term weight) versus how strongly it reflects your declared projects (raise active context weight) without a code change.

Infrastructure

Things that make the system more robust or flexible without changing the user-facing behaviour.

infra Decouple profile update from ingestion schedule low effort

Right now the profile update and LLM re-ranking activities run at the tail of NewsIntelligenceWorkflow, meaning they only run when new articles are ingested. If you want to run ingestion twice a week but update the profile at a different cadence, or trigger re-ranking on demand after you have been reading heavily, the current design makes that awkward.

The clean split: move update_user_news_profile, update_user_news_active_context, and rank_news_feed_with_llm into a dedicated NewsProfileUpdateWorkflow that runs on its own schedule. NewsIntelligenceWorkflow just calls it at the tail as a child workflow. Both can also be triggered independently via the internal API.

infra Multi-user support medium effort

The entire news feature is currently hardcoded to user_id = 1 in the worker activities and uses PlatformWorkerOptions.PrimaryUserId on the backend API routes. The data model already supports multiple users — every table has a UserId column and there are no singletons in the news schema. Extending to multiple users is mostly a matter of removing the hardcoded 1 from worker activities and reading the user ID from the JWT on the interaction and feed endpoints instead.

infra LLM output validation at write time low effort

Claude occasionally produces duplicate article IDs in the rankings. Currently this is handled defensively at read time in ListNewsFeedQueryHandler with a GroupBy. A cleaner fix is to catch it at write time: add a uniqueness check to StoreRankedNewsFeedCommandValidator that rejects any rankings list containing duplicate NewsItemId values. The worker can then retry or log a warning rather than storing bad data in the first place.

★
Where to start. Semantic deduplication and per-project topic lists are the highest-value, lowest-effort items on this list. Deduplication improves candidate quality for every subsequent phase immediately. Topic lists make the active context embedding significantly more specific. Both are purely additive and take an afternoon each. Everything else can wait.

01

What Phase 5 delivers

Cosine similarity is fast and effective, but it is fundamentally a measure of geometric closeness between vectors. It cannot reason. It does not know that an article about Temporal workflow architecture is relevant because you are building a Temporal-based worker system right now. It just knows the embeddings are close.

Phase 5 adds a reasoning layer. After the Phase 4 vector ranking produces a candidate set of 50 articles, Claude reads them alongside your full user context and re-ranks the top 20 with a relevance score and a one-sentence explanation written specifically to you. The result is stored in the database before you ever open the feed, so there is no added latency at read time.

Pre-computed, instant loading
Re-ranking happens in the worker at ingestion time, not when you open the feed. The ranked list is stored in the DB and served immediately — zero LLM latency on the feed request.
Explanation per article
Each article gets a one-sentence "why this matters to you" written by Claude, referencing your actual projects or interests. Not generic — specific to your context at the time of ranking.
Graceful fallback
If no pre-computed ranking exists (first run, or LLM call failed), the feed falls back to the Phase 4 vector search result exactly as before. Nothing breaks.

The backend only stores data — the LLM call itself stays in Python, consistent with how all other AI calls in the system work.

The LLM call

The system prompt frames Claude as a relevance judge for a specific reader. The user prompt passes the full interest context and the 50 candidate articles with their titles and body snippets. Claude selects the top 20, assigns a relevance score, and writes one sentence per article explaining the relevance in terms of the reader's actual situation.

system
You are ranking news articles for a specific reader based on their declared interests, goals, and active projects. Your job is to identify which articles are genuinely most valuable to this person right now and explain the relevance directly to them. Be specific — reference their actual projects and goals in the explanation, not generic interest labels. Return strict JSON only, no markdown outside of the JSON.
user
## Reader profile Core interests: software engineering, AI systems, distributed systems Secondary interests: embedded systems, career development Goals: backend engineering internship, production-quality projects Active projects: Platform, news feature ## Candidate articles (50, pre-ranked by vector similarity) [1] id="abc123" Title: "Building reliable distributed workflows with Temporal" Source: Engineering at Meta | Published: 2026-05-30 Snippet: Temporal's workflow engine provides durable execution guarantees... [2] id="def456" Title: "How embedding models encode semantic meaning" Source: Towards Data Science | Published: 2026-05-29 Snippet: When you embed a sentence, the model maps it to a point in... ... up to 50 articles ## Task Select the 20 articles that are most genuinely relevant to this reader right now. Rank them from most to least relevant. For each, provide: - score: integer 0–100 (higher = more relevant) - explanation: one sentence written directly to the reader, referencing their specific projects or goals Return JSON: {"rankings": [{"newsItemId": "...", "score": 94, "explanation": "..."}, ...]}
★
Specificity is the whole point. A generic explanation ("relevant to your interest in AI") adds no value. The prompt explicitly instructs Claude to reference the reader's actual projects and goals. An explanation like "Directly relevant to your news feature — the same embedding approach you are using for feed ranking" is what makes Phase 5 feel different from a scored list.

Candidate fetch

A new backend endpoint — GET /api/internal/v1/news/feed/candidates — runs the Phase 4 vector search internally to get the top 50 articles, then packages them with the user's interest context into a single response. The worker calls this once and gets everything it needs for the LLM prompt.

# Response shape — what the worker receives
{
  "userContext": {
    "coreInterests":     ["software engineering", "AI systems"],
    "secondaryInterests": ["embedded systems"],
    "goals":             ["backend internship"],
    "activeProjects":    ["Platform", "news feature"]
  },
  "candidates": [
    {
      "newsItemId":  "abc123",
      "title":       "Building reliable distributed workflows with Temporal",
      "source":      "Engineering at Meta",
      "publishedAt": "2026-05-30T08:00:00Z",
      "bodySnippet": "Temporal's workflow engine provides durable execution..."
    },
    ... up to 50
  ]
}
ℹ
Body snippet length. Each article body is truncated to 300 characters in the candidate response. This keeps the total prompt size manageable (50 articles × ~400 chars ≈ 20k chars, well within Claude's context window) while giving enough signal to judge relevance. The full body is not needed for ranking — the title plus a snippet is sufficient.

Domain — NewsRankedFeed

One new entity stores the pre-computed ranked list per user. One row per user, completely replaced on each ingestion run. Using JSONB for the entries avoids a join table and keeps the feed read to a single row lookup.

// Platform.Domain/Features/News/NewsRankedFeed.cs
public sealed class NewsRankedFeed
{
    /// <summary>PK — one ranked feed per user.</summary>
    public int            UserId     { get; set; }

    /// <summary>
    /// Ordered JSON array of ranked entries. Each entry:
    /// { newsItemId, score, explanation }
    /// Stored as JSONB and deserialized in the query handler.
    /// </summary>
    public string         EntriesJson { get; set; } = "[]";

    /// <summary>The Anthropic model that produced this ranking.</summary>
    public string         ModelUsed  { get; set; } = "";

    public DateTimeOffset RankedAt   { get; set; }
}

EF Core configuration

Table name: news_ranked_feeds. EntriesJson mapped as jsonb. ModelUsed max length 128. UserId is the primary key — no identity column, since the row is always upserted by user.

3. GetNewsFeedCandidatesQuery + Handler

This is the read side that the worker calls before the LLM step. It runs the Phase 4 vector search internally, fetches the article metadata, and loads the user interest context — all in one backend call so the worker only makes one HTTP request before the LLM call.

// Platform.Application/Features/News/RankedFeed/GetNewsFeedCandidatesQueryHandler.cs
public sealed class GetNewsFeedCandidatesQueryHandler(
    INewsVectorSearch   vectorSearch,
    INewsReadRepository newsRepo,
    IUserInterestProvider interests)
{
    public async Task<NewsFeedCandidatesDto> HandleAsync(
        GetNewsFeedCandidatesQuery query, CancellationToken ct)
    {
        // Run the Phase 4 vector search for a larger candidate pool
        var hits  = await vectorSearch.RankByRelevanceAsync(query.UserId, query.Limit, ct);
        var items = await newsRepo.GetByIdsAsync(hits.Select(h => h.NewsItemId), ct);

        // Package user context alongside candidates
        var snapshot = await interests.GetInterestsAsync(query.UserId, ct);

        return new NewsFeedCandidatesDto(
            UserContext:  BuildContext(snapshot),
            Candidates:   items.Select(x => ToCandidate(x)).ToList());
    }
}

4. Update ListNewsFeedQueryHandler — check pre-computed ranking first

The feed endpoint gains awareness of the pre-computed ranking. If one exists, it fetches the ranked articles by ID in order and attaches the stored explanations. If not, it falls back to the Phase 4 vector search path. The fallback means the feed is never broken — Phase 5 only ever adds to it.

public async Task<IReadOnlyList<NewsItemSummaryDto>> HandleAsync(
    ListNewsFeedQuery query, CancellationToken ct)
{
    // Phase 5: use pre-computed LLM ranking when available
    var ranked = await rankedFeedRepo.GetAsync(query.UserId, ct);
    if (ranked is not null)
    {
        var entries   = JsonSerializer.Deserialize<List<RankedFeedEntry>>(ranked.EntriesJson)!;
        var ids       = entries.Select(e => e.NewsItemId);
        var items     = await news.GetByIdsAsync(ids, ct);
        var itemMap   = items.ToDictionary(x => x.Id);
        var scoreMap  = entries.ToDictionary(e => e.NewsItemId, e => e.Score / 100.0);
        var exMap     = entries.ToDictionary(e => e.NewsItemId, e => e.Explanation);

        return entries
            .Where(e => itemMap.ContainsKey(e.NewsItemId))
            .Select(e => itemMap[e.NewsItemId] with
            {
                RelevanceScore      = scoreMap.GetValueOrDefault(e.NewsItemId),
                RelevanceExplanation = exMap.GetValueOrDefault(e.NewsItemId),
            })
            .ToList();
    }

    // Phase 2–4 fallback — vector search, no explanations
    var hits = await vectorSearch.RankByRelevanceAsync(query.UserId, FeedLimit, ct);
    // ... existing fallback logic unchanged
}

New dependency: anthropic

The Anthropic Python SDK is added to pyproject.toml. The worker already uses httpx for all other HTTP calls, but the Anthropic SDK handles auth, retries, and response parsing cleanly. A new ANTHROPIC_API_KEY environment variable is required.

# pyproject.toml — add to dependencies
"anthropic>=0.28.0"
act 1 Python rank_news_feed_with_llm timeout 120s

Fetches candidates from the backend, calls Claude to re-rank, posts results back. The longer timeout (120s vs 30s for other activities) accounts for the LLM call latency. The activity never raises on a graceful failure — if the Anthropic call fails or returns unparseable JSON, it logs and returns "error" so the workflow continues and the feed falls back to vector search.

  • Accepts user_id: int, candidate_limit: int = 50, final_limit: int = 20
  • GETs /api/internal/v1/news/feed/candidates?userId=1&limit=50
  • Builds prompt from user context + candidate articles
  • Calls anthropic.messages.create(model="claude-sonnet-4-6", ...)
  • Parses JSON response: {"rankings": [{newsItemId, score, explanation}, ...]}
  • POSTs to /api/internal/v1/news/feed/ranked-results
  • Returns {"status": "ranked"} or {"status": "error"}
@activity.defn
async def rank_news_feed_with_llm(
    user_id: int,
    candidate_limit: int = 50,
    final_limit: int = 20,
) -> dict:
    settings = get_settings()
    base     = settings.platform_api_base_url.rstrip("/")
    headers  = {"Authorization": f"Bearer {settings.platform_internal_service_token}"}

    # 1. Fetch candidates + user context
    async with httpx.AsyncClient(timeout=30.0) as client:
        r = await client.get(
            f"{base}/api/internal/v1/news/feed/candidates",
            params={"userId": user_id, "limit": candidate_limit},
            headers=headers,
        )
        r.raise_for_status()
        data = r.json()

    candidates = data.get("candidates", [])
    user_ctx   = data.get("userContext", {})

    if not candidates:
        logger.info("rank_news_feed_with_llm: no candidates, skipping")
        return {"status": "no-candidates"}

    # 2. Call Claude
    system_prompt = _build_system_prompt()
    user_prompt   = _build_user_prompt(user_ctx, candidates, final_limit)

    try:
        client = anthropic.AsyncAnthropic(api_key=settings.anthropic_api_key)
        message = await client.messages.create(
            model="claude-sonnet-4-6",
            max_tokens=4096,
            system=system_prompt,
            messages=[{"role": "user", "content": user_prompt}],
        )
        raw      = message.content[0].text
        rankings = json.loads(raw)["rankings"]
    except Exception:
        logger.exception("rank_news_feed_with_llm LLM call failed")
        return {"status": "error"}

    # 3. Store ranked results
    async with httpx.AsyncClient(timeout=30.0) as client:
        r = await client.post(
            f"{base}/api/internal/v1/news/feed/ranked-results",
            json={
                "userId":   user_id,
                "modelUsed": "claude-sonnet-4-6",
                "rankings": rankings,
            },
            headers=headers,
        )
        r.raise_for_status()

    logger.info("rank_news_feed_with_llm ranked %d articles", len(rankings))
    return {"status": "ranked", "count": len(rankings)}

Frontend — show explanations

The only frontend change is displaying relevanceExplanation when it is present in the API response. The field is already threaded through NewsItemSummaryDto — it just needs to be rendered.

The explanation should appear as a small line of text below the article title, visually distinct from the body snippet — think of it as a personal annotation, not a description. A muted font size and the accent colour work well here. No new component is needed; it is a conditional render inside the existing article card.

// Inside the article card in NewsView.tsx — conditional explanation line
{article.relevanceExplanation && (
  <p className={styles.explanation}>
    {article.relevanceExplanation}
  </p>
)}
ℹ
No loading state needed. The explanation is either in the API response or it is not. There is no async fetch per article. If the ranked feed exists, every card has an explanation. If the feed falls back to vector search, no cards have explanations. The UI should handle both states without branching logic beyond the conditional render.

!
Decision — candidate limit vs final limit. The plan uses 50 candidates re-ranked to 20. Raising the candidate limit gives Claude more material to choose from but increases prompt size and cost. Lowering the final limit keeps the feed tight but may miss good articles. Both are constants passed to the activity — easy to tune without code changes once you see the quality of results.
!
Decision — staleness of the ranked feed. The ranked list is computed once per ingestion run (currently weekly). Articles from the previous run remain in the ranked feed until the next run. This is acceptable because the underlying article pool also only changes on ingestion runs — you are never showing a ranking for a set of articles that no longer matches what is in the DB. If you move to twice-weekly ingestion, the ranking refreshes twice as often automatically.
ℹ
This is the final phase. Phase 5 completes the news intelligence feature as originally designed. The full pipeline is: fetch (Phase 1) → embed + rank by similarity (Phase 2) → behavioral feedback (Phase 3) → dual interest model + active context (Phase 4) → LLM re-ranking + explanations (Phase 5). Post-Phase 5 extensions from the original plan (novelty scoring, multi-armed bandit, Neo4j knowledge graph) are additive and do not require changes to any Phase 1–5 infrastructure.

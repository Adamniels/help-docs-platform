Key reuse opportunity

Your memory system already has a full pgvector embedding pipeline: IMemoryEmbeddingGenerator, IMemoryVectorRecallSearch, and the MemoryEmbedding entity with its migration. The news embedding layer follows the exact same pattern — you're adding a NewsItemEmbedding entity, not starting from scratch on the vector infrastructure.

02

Pipeline overview

Five phases, each one adding a distinct capability to the feed. Every phase delivers something tangible you can use immediately — you won't be waiting until Phase 5 to see results.

End-to-end pipeline — all five phases

Phase 1

Real ingestion

RSS feeds, NewsAPI, arXiv. Temporal activities fetch and store articles with full body text.

Phase 2

Semantic scoring

Articles get embedded on ingest. User profile is a vector. Feed is ranked by cosine similarity.

Phase 3

Feedback loop

Dwell time and saves update the interest profile. System starts learning from your behavior.

Phase 4

Dual interest model

Long-term and short-term profiles. Active project contexts boosted. Hierarchical interest tree.

Phase 5

LLM re-ranking

Claude Sonnet re-ranks the top candidates. Each article gets a "why this matters" explanation.

Build philosophy

Each phase is independently shippable. After Phase 1 you have a real news feed. After Phase 2 it's already personalized. The later phases make it significantly smarter, but you're not blocked on them to see value. Build in order, validate each phase before moving to the next.

03

Prerequisite — two small things before Phase 1

ExplicitUserProfile stays exactly where it is. It is explicit memory — the user declaring who they are and what they care about, with an authority weight and conflict resolution built around it. Moving the data would be risk for no real gain. The two actual problems are much smaller: the news feature needs a clean way to read interests without depending on Memory internals, and the frontend should expose interests editing under Profile rather than buried in a memory sub-route.

Backend — abstraction layer

  • Add IUserInterestProvider interface in Platform.Application.Abstractions.News with a single method: GetInterestsAsync() returning a plain DTO with core interests, secondary interests, goals, and active projects
  • Implement it in Infrastructure by reading from the existing IExplicitUserProfileRepository — no schema change, no migration, no domain move
  • The news feature (Phase 2 onwards) depends only on IUserInterestProvider — it never touches the Memory module directly
  • ExplicitUserProfile unchanged — memory consumers keep reading it the same way they do today

Frontend — surface interests under Profile

  • Add a Profile page (or section) in the frontend where interests, goals, and active projects can be viewed and edited
  • The API call underneath stays the same — it still hits the existing memory/profile endpoint. Only the navigation and page placement changes
  • No backend route changes, no migration, no data moved
  • The memory/profile route can stay alive for as long as needed — nothing breaks

Why keep it in Memory

ExplicitUserProfile is genuinely explicit memory — it's the highest-authority, user-declared source of truth that the conflict detector and context provider both rely on. The authority weight, the contradiction resolution, the structured validation — all of that belongs in memory because it's memory infrastructure. What the news feature needs is not ownership of this data, just a clean read path to it. The IUserInterestProvider abstraction gives you that without touching anything that's already working.

Phase 3
Behavioral feedback loop
Track how you interact with articles. Update your interest profile automatically. The system starts learning.
▼

What gets built

  • F Track dwell time in NewsView.tsx: start a timer when an article opens, stop when closed. Track saves (a save button in the detail view). Send these as interaction events to the backend.
  • B Add POST /api/v1/news/interactions endpoint. Accepts interaction type (read, save, dismiss) and dwell seconds.
  • B Create NewsInteraction entity to store each event: article ID, type, dwell seconds, timestamp.
  • B Add a scheduled Temporal workflow (daily or on-demand) that reads recent interactions, computes a weighted average of the article embeddings (strong signal = full weight, dismiss = negative weight), and updates the UserInterestProfile embedding.
  • B Normalize dwell time against your personal reading baseline (average across all your reads) before applying weight — so absolute time doesn't distort signals.

Phase 4
Dual interest model + active contexts
Split long-term and short-term interest profiles. Inject your active projects as context boosters.
▼

What gets built

  • B Split UserInterestProfile into two embeddings: LongTermEmbedding (updated weekly, exponential decay over time) and ShortTermEmbedding (sliding window of last 14 days, no decay). The ranking layer blends both with configurable weights.
  • B The ActiveProjects already moved to UserInterestProfile in the prerequisite step. Phase 4 extends this into a richer active-context model: each project gets an associated topic list for ranking boosts. Example: [{ "label": "news feature", "topics": ["recommendation systems", "embeddings", "temporal"] }]. Update UserInterestV1Routes with a dedicated active-contexts endpoint.
  • B Implement hierarchical interest tree: coarse domains (AI, software architecture, Swedish tech) each with sub-interest weights. Stored as JSON in the profile. Used in the ranking score as a secondary dimension alongside the embedding similarity.
  • F Add a simple settings panel to edit active contexts — just a text field or tag input. When a new project starts, you add it here and the feed immediately starts surfacing relevant articles.

05
Advanced
LLM re-ranking + explanations
Claude Sonnet re-ranks the top candidates and generates a "why this matters to you" note per article.
▼

What gets built

  • W Add an llm_rerank Temporal activity. It receives the top 30 candidates from the vector search, your current interest profile and active contexts, and calls Claude Sonnet via the Anthropic API. The LLM returns a ranked list with a 1–2 sentence relevance explanation per article.
  • B Add RelevanceExplanation (string) to NewsItemSummaryDto. The explanation is generated fresh on each feed refresh and is not stored permanently.
  • B The prompt to Claude should include: your interest tree, active contexts, recent saves, and the article's title and summary. Keep it under ~800 tokens to control cost. Use claude-sonnet-4-6.
  • F Show the relevance explanation in the article detail view — a clearly labelled "Why this matters" block. This is the moment the feed stops feeling like an aggregator and starts feeling like an intelligence layer.
  • W Make re-ranking optional and cacheable: run it as part of the scheduled ingest workflow (not per-request) and store the explanation alongside the ranked order. This avoids per-request LLM latency.

Stack — what you're using and why

This plan stays within your existing stack throughout. No new databases or runtimes are introduced until Phase 4 and 5 optionally consider a graph layer — and even then it's additive, not a replacement.

Layer Technology Status Used for in news
Backend API .NET 10, C#, EF Core Running Feed endpoint, ingestion endpoint, interaction recording, profile management
Database PostgreSQL + pgvector Running Article storage, embedding vectors, interest profile, interaction events
Worker runtime Python, Temporal Running Ingestion activities, embedding activity, profile update workflow, LLM re-ranking
Embeddings OpenAI text-embedding-3-large or Voyage-3 Phase 2 Embedding articles and the user interest profile. Same embedding model for both so cosine similarity is meaningful.
LLM re-ranking Claude Sonnet 4 (claude-sonnet-4-6) Phase 5 Re-ranking top candidates, generating relevance explanations per article
News sources RSS (feedparser), GNews API, arXiv Phase 1 Ingesting raw articles. feedparser for RSS, GNews for broad coverage, arXiv for research papers
Frontend Next.js, TypeScript Running News feed UI, article detail view, interaction tracking, settings panel

One thing to decide before Phase 2

You need to pick one embedding model and stick with it — articles and the user profile vector must be embedded with the same model or cosine similarity doesn't work. OpenAI's text-embedding-3-large (1536 dimensions) is the safe default. Voyage's voyage-3 is reportedly better on retrieval benchmarks at a lower cost per token. Decide before Phase 2 starts, as changing models later requires re-embedding everything.

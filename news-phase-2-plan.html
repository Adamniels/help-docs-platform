01

What Phase 2 delivers

Today the news feed is a chronological list — all sources contribute equally, no article is more relevant to you than any other. After Phase 2, every article is embedded on ingest and the feed is ranked by cosine similarity against your personal interest profile vector. The feed stops being a list and starts being a relevance-ordered view of what matters to you right now.

Phase 2 also establishes a critical piece of shared infrastructure: the OpenAI embedding provider. The memory system already defines IMemoryEmbeddingGenerator but only has a deterministic stub wired in. Phase 2 implements the real OpenAI provider once, designed to be registered for both memory and news so neither system duplicates the integration.

Articles embedded on ingest
Every newly ingested article gets embedded immediately as part of the workflow run. Embeddings are stored in pgvector alongside the article.
User interest profile
Seeded once from your explicit interest profile (core interests, secondary interests, goals, active projects). Stored as a 1536-dim vector.
Ranked feed
The feed endpoint runs an ANN cosine similarity search against your profile vector and returns articles ordered by relevance, not date.
Relevance score visible
Each article in the feed response now carries a relevance score (0–1). The frontend shows it as a subtle indicator on the news card.
02

Pipeline overview

Phase 2 adds two steps to the existing workflow — embedding and profile seeding — and changes the read path to use vector search instead of a date sort.

existing — phase 1
Fetch + ingest
Four source activities run in parallel. Results are deduped and POSTed to the backend. ingest_articles returns a list of newly created article IDs.
new — phase 2
Embed new articles
embed_news_articles receives only the newly created IDs (not duplicates). Calls OpenAI embeddings API, POSTs vectors to backend. Duplicates are skipped — they already have embeddings.
new — phase 2 (runs once)
Ensure user news profile
ensure_user_news_profile checks if a profile vector exists for the user. If not, reads from IUserInterestProvider, embeds the interest text, and stores as the initial long-term profile. Idempotent — safe to call every run.
updated read path
Ranked feed query
GET /api/v1/news/feed now loads the user's profile vector and runs a pgvector cosine similarity search. Returns top 30 articles ordered by relevance with scores attached.
↻ Only new articles are embedded per run. The workflow passes the created IDs from ingest_articles directly to embed_news_articles — duplicates already have embeddings and are skipped entirely. This keeps each run cheap regardless of how many articles are already in the database.

New data model

Two new entities are added. Both follow the same patterns as the memory system's MemoryEmbedding entity — same pgvector column type, same 1536-dimension constant, same EF Core configuration approach.

The memory system defines IMemoryEmbeddingGenerator but only has a deterministic stub wired in production. The real OpenAI implementation does not exist yet. Phase 2 adds it once, designed to serve both the news and memory embedding pipelines without duplication.

Worker — new activities and contracts

Two new Temporal activities added to activities.py. Both are short — the heavy work (embedding generation, vector storage) happens in the backend. The worker's job is to pass the right data and handle errors gracefully.

act 1 Python embed_news_articles timeout 120s

Receives the list of newly created article IDs from the workflow. POSTs each ID to the backend endpoint POST /api/internal/v1/news/items/{id}/embed concurrently. The backend fetches the article body, generates the embedding, and stores it — the worker never handles float arrays.

  • Accepts article_ids: list[str] — only the created IDs, not duplicates
  • Concurrency capped at 5 simultaneous requests (embedding is slower than ingest)
  • Per-article errors are caught and counted — never abort the whole batch
  • Returns NewsEmbedResult(embedded: int, skipped: int, errors: int)
# workers-platform/app/workflows/news_intelligence/activities.py
@activity.defn
async def embed_news_articles(article_ids: list[str]) -> dict:
    settings = get_settings()
    base = settings.platform_api_base_url.rstrip("/")
    headers = {"Authorization": f"Bearer {settings.platform_internal_service_token}"}
    sem = asyncio.Semaphore(5)
    embedded = skipped = errors = 0

    async def embed_one(client, article_id):
        async with sem:
            r = await client.post(
                f"{base}/api/internal/v1/news/items/{article_id}/embed",
                headers=headers,
            )
            return r.json().get("status")  # "embedded" | "skipped" | "error"

    async with httpx.AsyncClient(timeout=30.0) as client:
        results = await asyncio.gather(
            *(embed_one(client, aid) for aid in article_ids),
            return_exceptions=True,
        )

act 2 Python ensure_user_news_profile timeout 30s

Checks whether the user already has a news profile vector. If one exists, does nothing. If not, POSTs to the backend seed endpoint which reads from IUserInterestProvider, generates the embedding server-side, and stores it. Safe to call on every workflow run.

  • Accepts user_id: int — passed from workflow config (the primary user, same as memory consolidation)
  • Calls POST /api/internal/v1/news/profile/seed
  • Backend returns "seeded" (first time) or "exists" (already seeded)
  • Logs the outcome, never raises — a missing profile degrades gracefully to chronological feed

Workflow changes

The workflow gains two additional steps after the existing ingest activity. The key change is threading the list of newly created article IDs from ingest_articles into embed_news_articles.

        results = await workflow.asyncio.gather(
            workflow.execute_activity("fetch_rss_articles", ...),
            workflow.execute_activity("fetch_hacker_news_articles", ...),
            workflow.execute_activity("fetch_gnews_articles", ...),
            workflow.execute_activity("fetch_arxiv_articles", ...),
            return_exceptions=True,
        )
        unique = # ... dedupe logic unchanged ...

        ingest_raw = await workflow.execute_activity("ingest_articles", unique, ...)
        ingest_result = NewsIngestResult.model_validate(ingest_raw)

        # ── new Phase 2 steps ────────────────────────────────────
        # Only embed articles that were actually created this run
        if ingest_result.created_ids:
            await workflow.execute_activity(
                "embed_news_articles",
                ingest_result.created_ids,
                start_to_close_timeout=timedelta(minutes=2),

            request.user_id or 1,
            start_to_close_timeout=timedelta(seconds=30),
        )

Vector search interface and implementation

// Platform.Application/Abstractions/News/INewsVectorSearch.cs
public interface INewsVectorSearch
{
    Task<IReadOnlyList<NewsVectorHit>> RankByRelevanceAsync(
        int userId,
        int limit,
        CancellationToken ct = default);
}

public sealed record NewsVectorHit(
    string NewsItemId,
    double CosineSimilarity);   // 0–1, higher = more relevant
// Platform.Infrastructure/Features/News/NewsVectorSearch.cs
// Mirrors EfMemoryVectorRecallSearch — same pgvector cosine distance pattern
var profile = await db.NewsUserProfiles
    .FirstOrDefaultAsync(p => p.UserId == userId, ct);

if (profile is null) return []; // no profile → caller falls back to date sort

var qv = profile.LongTermEmbedding;
return await db.NewsItemEmbeddings
    .Where(e => e.EmbeddingModelKey == modelKey)
    .OrderBy(e => e.Embedding!.CosineDistance(qv))
    .Take(limit)
    .Select(e => new NewsVectorHit(
        e.NewsItemId,
        1.0 - (double)e.Embedding!.CosineDistance(qv)))
    .ToListAsync(ct);

Updated feed query handler

The read path now has two branches: vector-ranked (when a profile exists) and chronological (fallback). The caller never knows which branch ran — the response shape is identical.

// Platform.Application/Features/News/ListFeed/ListNewsFeedQueryHandler.cs
var hits = await _vectorSearch.RankByRelevanceAsync(userId, limit: 30, ct);

if (hits.Count == 0)
{
    // No profile yet — fall back to chronological
    return await _newsReadRepository.ListFeedAsync(limit: 30, ct);
}

var scoreMap = hits.ToDictionary(h => h.NewsItemId, h => h.CosineSimilarity);
var items    = await _newsReadRepository.GetByIdsAsync(hits.Select(h => h.NewsItemId), ct);

return items
    .OrderByDescending(x => scoreMap.GetValueOrDefault(x.Id))
    .Select(x => x.ToSummaryDto(relevanceScore: scoreMap.GetValueOrDefault(x.Id)))

Done when

Phase 2 is complete when all of the following are true:

  • □A workflow run produces log lines: embed_news_articles done embedded=X skipped=0 errors=0
  • □The news_item_embeddings table has rows with 1536-dim vectors
  • □The news_user_profiles table has one row with a non-null embedding
  • □GET /api/v1/news/feed returns articles in relevance order (not purely chronological)
  • □Each article in the feed response has a non-null relevanceScore between 0 and 1
  • □The frontend shows the relevance score indicator on news cards
  • □A second workflow run skips already-embedded articles (skipped=X in the log)

What Phase 3 unlocks

Once the interest profile vector and article embeddings are in place, Phase 3 (behavioral feedback loop) can update the profile vector based on how you actually interact with articles — dwell time, saves, dismissals. The profile starts static (seeded from your declared interests) and becomes dynamic.
